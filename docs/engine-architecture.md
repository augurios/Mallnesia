# Engine architecture

Next.js (App Router) + TypeScript, static export. The game engine is plain Three.js with no React imports; React only draws the UI around it. dirien/backrooms is a structural reference only (no license, no code copied).

## Layout

- `src/app/` — Next.js UI. `page.tsx` renders `GameLoader`, which loads `GameCanvas` client-side only (`ssr: false`), since the engine needs `window` and WebGL. `GameCanvas` mounts the engine and shows the menu/hint overlay.
- `src/engine/` — framework-free TypeScript. Today: `runtime.ts` (renderer, loop, first-person look, input, doors, audio) and `props.ts` (kit pieces placed through the mall: one `InstancedMesh` per piece per floor, plus a collider per instance) and `walk.ts` (collision and ground-following, with no rendering and no DOM, so `scripts/test-walk.mts` runs the exact code the game runs). The player is pushed out of walls horizontally by a `three-mesh-bvh` sphere test; its height follows the ground via a downward ray against the floor and stair meshes (step up 0.5 m, otherwise gravity); the floor index is derived from that height. Colliders and ground are picked by material name, not node name: the loader makes node names unique for chunks (`walls`, `walls_1`, ...). Planned modules, mirroring the reference:
  - `input.ts` (keyboard, mouse, touch), `audio.ts`, `sanity.ts`, `lighting.ts` (baked plus flashlight with charge), `quality.ts` (presets, `?quality=`)
  - `levels/` (registry, lazy loading; the mall and the garage as separate levels)
  - `world/` (GLB loading, `three-mesh-bvh` collision, garage chunk generator)
  - `entities/` (shadow, girl in white, watchers, guard)
  - `save.ts` (versioned, tolerant of blocked storage)
- Look (see `docs/art_style_reference.md`, "How the base project gets its look"): `materials.ts` adds procedural surface detail to the blockout's materials in world space (porcelain tiles with granite inserts and glossy grout, plaster with skirting and corner darkening, ceiling panels, stained concrete), keyed by the material names in `scripts/blockout/palette.mts`. `post.ts` is the finishing pass (bloom, film grain, vignette, color drain) on top of ACES tone mapping and a hemisphere sky-glow light. Quality presets switch detail, bloom and film individually; low renders straight to the screen. Debug: `?ambient=`, `?exposure=`, `?hud=off`, `?stats=1` (triangles and draw calls per frame, all passes), `?lod=<meters>` (kit piece LOD distance: 0 draws all far, 999 all near), `?epx=1` (exploration mode: the flashlight and stamina never run out, for testing).
- `src/engine/view.ts` — view settings saved in local storage: mouse sensitivity (0.3 to 2) and camera motion (head bob, plus a slight FOV widening while running). Camera motion starts off when the system asks for reduced motion. The camera itself lives in `runtime.ts`. It uses an 80° vertical FOV (`?fov=` to try others). Movement eases in and out (`ACCEL`), so starting and stopping never jolt. Frames are capped at 50 ms. The first mouse event after the pointer locks is dropped, and so are glitch spikes.
- `src/engine/sky.ts` — the world outside the glass: one procedural shader on a dome that follows the camera (overcast night sky with city glow, far hills, a ring of blocks with lit windows, street-lit ground, distant headlights). No texture files, no parallax, dim on purpose; the fog does not touch it.
- `src/engine/sanity.ts` — the sanity rules (no DOM, no Three.js, tested by `npm run test:sanity`): darkness (flashlight off) drains after a grace period, light restores, `drain()` and `setDrain()` for apparitions and watchers. It outputs `look` (tiers that switch on in order as sanity falls: wobble, color fringing, tunnel pinch, ghost image, shake; `post.ts` draws them in the one film pass, only on medium and high) and `shift` (how much faster the mall changes doors; `doors.tempo`). With camera motion off, the moving tiers are dropped (`stillLook`). Debug: Z / X lower / raise it, `?sanity=` starts at a level, `?stats=1` shows it; `npm run shots` has `sanity_*` views. The ideas follow the reference's tiered post shader; the code is our own.
- `src/engine/stamina.ts` and the HUD — stamina (no DOM, no Three.js, tested by `npm run test:stamina`): running (Shift) drains 0.23/s, resting refills 0.15/s; at 0 the player is exhausted and cannot run until it is back to 0.3. Reset on load, respawn and faint. The runtime sends `stamina`, `exhausted` and `sanity` in `PlayerStatus`; `GameCanvas.tsx` draws the bottom-left vitals block (Cordura with a percentage, Aguante, Linterna) as `<meter>` bars in the reference's style (small caps labels, thin bars, muted gold); sanity under 30% and exhaustion turn red and pulse. `?hud=off` hides it.
- `src/engine/save.ts` and `src/engine/atrium.ts` — save/load (no DOM, no Three.js, tested by `npm run test:save`). `save.ts`: a small versioned save (position, height, facing, area, notes read, guard and exit progress; never sanity or flashlight charge) in two slots, `checkpoint` and `manual`, in local storage (`elmallvivo.save.<slot>`). A newer or broken save is ignored, old versions go through a migration step, and if storage is blocked or full the save lives in memory for the visit. `atrium.ts`: `AtriumTracker` fires `entered` and `left` when the player crosses into or out of the atrium rectangles (the `atrium_a` and `atrium_b` boxes of the plans, both count, decided by Augusto; leaving needs 1.5 m past the edge so the edge never spams). The runtime writes the checkpoint on `entered` only (leaving saves nothing) and exposes `save()`, `load(slot)` and `savedAt(slot)` to the pause menu. `save()` is refused while `hunted()` is true (the shadow card sets it). Loading puts sanity and the flashlight back to full. The `garage` area is saved but not loadable until that level exists.
- `src/engine/girl.ts`, `src/engine/girl-view.ts` — the girl in white (tested by `npm run test:girl`): a lost child crying for her parents. She never moves, never chases, never catches. `GirlDirector` times her (first 100 to 160 s in, then 150 to 320 s after each one ends, divided by 1 + 0.5 × the sanity shift level). `pickGirlSpot` puts her 6 to 12 m from the player, in the open and in line of sight but **out of the view** (at least 70° off where they face), so she is found by turning around. Half the time (`AHEAD_CHANCE`, when a place exists) `pickHiddenAhead` puts her **ahead** instead, 5 to 12 m away within 40° of the view but with no line of sight (behind a wall, corner or column) and a walk no longer than 2.5× the distance + 4 m, so the player finds her by walking round the obstacle; `chooseGirlSpot` makes the pick. An `Apparition` fades in unseen (0.6 s), cries (`audio.girl()`: a looping sob that follows her) and **calls out** every 7 to 11 s (a wailing "ma-má" plus a subtitle from `es.girlCalls`). Seeing her (in the frustum, with line of sight) costs 3% sanity the first time and then `girlDrain(distance)` per second: 1.2%/s at 20 m up to 7%/s at 2 m or less, growing with the square of how close the player is; seeing her from within 1.5 m (`TOUCH_DIST`) sets sanity to 0 at once, so the player faints (the usual out-of-sanity fail). She stays until the player walks past 20 m (fades out in 1.2 s); if never seen she gives up after 75 s. Walking up to her does not make her vanish. She is held back during the guard's scene and while the shadow hunts. `girl-view.ts` is placeholder art: a child-sized figure in a pale dress with dark hair, unlit and translucent. `kind` (`corridor`, `elevator`, `mirror`, `bathroom`) is reserved: only corridors exist until elevators, mirrors and bathrooms are built. Debug: **U** calls her now (behind you), `?girl=off`, `?girl=now` (first in 3 s), `?girlat=x,y` (places her, screenshots `girl_*`).
- `src/engine/garage-gen.ts`, `src/engine/garage-view.ts` — the parking garage, a level of its own (tested by `npm run test:garage`). `generateGarage(seed)` (pure) builds a 7 × 4 grid of 12 m column bays: a random spanning-tree maze with 30% extra openings (loops, so the van can be passed again), a 6 m or 10 m doorway in each opened wall, walls and columns as axis-aligned boxes (the collision: `resolveGarage` pushes a 0.35 m circle out of them), painted stalls and parked cars in slots along the north and south walls (never across a doorway: 61 cars), three dead ends (some with a ramp that climbs into the ceiling), four fluorescent tubes per bay (62% on, 22% flicker, 16% dead), the stairwell door in the west wall where the player appears, and the attendant's booth with the payphone at the east end. The guided path (BFS from the stairwell door to the farthest cell of the last column, 14 cells) is checked to be really walkable by a body (the test walks it, on the default seed and on 25 others). The generic minivan (faded green, cream band, roof rack) stands in three cells along that path; the level signs along it read P2, P2, P3, P3, P7, P-12 ...; "Salida" arrows point the right way at first and, after 45% of the path, mostly into walls. Default seed `GARAGE.SEED` = 1995, fixed, is the base: each of the six strip openings (2 x 3 floors) has its own garage, `entranceSeed(base, opening, floor)` = base + (opening index x 3 + floor index - 4) x 7919 (the south opening on floor 2, the one the debug key uses, keeps the base seed itself), so the same door always leads to the same garage. Ramps: `generateGarage` gives every garage at least `GARAGE.RAMPS_MIN` (2) ramps, closing off cells away from the guided path down to one doorway when the maze has too few dead ends (on a random stream of its own, so the rest of the layout is unchanged). A ramp is a 6 x 11.4 m wedge from the doorway wall (foot) to the far wall, rising `GARAGE.RAMP_RISE` (3 m); cars, stalls, tubes and the "Salida" arrow in that cell are removed. The player really walks up it: collision leaves ramp boxes out (`garage.solid`), `rampHeight` gives the floor height and the runtime sets `player.y` to it (the eye follows), and the view cuts a hole in the ceiling over the ramp from 0.9 m up (`rampHole`; the ceiling is a `ShapeGeometry`). The ramp up is seamless. `generateGarage(seed, { arrival: true })` makes the next garage (no booth, no payphone, no ramps, no door: the first column's west wall has an open 6 m doorway) with a `landing`: the farthest cell that can be made a dead end (the entry cell's edges are never closed) holds a ramp *from below*, the same 6 x 11.4 m shape, its top flush with the floor and facing the only doorway; `rampHeight` there runs from -3 m at the foot to 0 at the top, the floor has a hole over it (`createGarageView`, a `ShapeGeometry`), and the view keeps a hidden pit (the wedge sunk 3 m, shaft walls; `setPit`). `pitBoxes` is its collision: walls along the sides and foot while the player is in it, and once they step out the whole pit is shut (`garage.pitShut`, `refreshSolid`). When the player comes within 9 m of a ramp, the runtime builds that garage (`prepRamp`, a random seed, or `?rampseed`) and lines it up: turned by the difference of the two ramps' headings (`delta`), translated so the landing's rectangle lies on the ramp's, and a ramp's rise above (`group.rotation.y`, `group.position`), pit hidden (the old ramp is the one on screen); it is dropped when the player is 16 m away. Through the ceiling's hole the player sees it. At `GARAGE.RAMP_SWAP` (1.9 m, the eye above the ceiling) `adoptRamp` makes it the world: its group goes back to the origin, the player's position, heading (`yaw -= delta`), velocity and eye (`eyeY -= RAMP_RISE`) are mapped into its frame, the old garage hides and the pit shows, so nothing changes on screen (the test checks that the landing's rectangle lines up over every ramp). `?rampswap=off` keeps the swap from happening, to compare the two views. The exit shows the real mall: the mall's objects (blockout, props, noise events) live in `mallRoot`; in an arrival garage `showArea` turns it half a turn into the garage's frame (`garageToStrip`, minus the floor's height), clips it to what lies outside the doorway (`mallClip`, a local clipping plane on every mall material, kept far away when unused so no shader recompiles) and points the surface shaders' world-position lookups back through `setMallFrame` (`mallFrame` uniform in `materials.ts`; patterns and the baked AO are looked up in the mall's own coordinates). `exitPen` is a 2.8 m pen of collision boxes outside the doorway (the mall's collision does not run until the swap); `swapToMall` happens at x < -2 once `exitInView` says the doorway is off screen (otherwise the pen holds the player). Debug: `?area=ramp`, `?rampseed=<n>`, `?ramptarget=north:3`. The runtime builds all six strip dressings at load (`buildStrip`, one view per place, each that seed's own first column) and each full garage the first time the player is inside its strip (`garageFor`, hidden, cached; the swap then only shows it); `?garageseed=random` or `?garageseed=<n>` changes it. `garage-view.ts` (placeholder shapes) merges everything static into a few meshes (about 19k triangles, 67 draw calls in the worst view) and instances the tubes and their light pools, with flicker. Runtime: the garage is built once at load, hidden, and swapped in behind the fade (`Fail` reasons `to_garage` and `to_mall`): the mall, its props, the sky, noise events and the guard are hidden, the shadow is sent away for 60 s, doors, atrium and hiding do not run. It is entered seamlessly, by walking into the parking strip (decided by Augusto: any opening, on any floor, any time; the way out is seamless too). The strip (x 3 to 15, y 84 to 180) is dressed as the garage's own first column: the entry row is fixed (`GARAGE.ENTRY_ROW` = 1), the strip is exactly one 12 m cell wide, and its two 6 m openings (`GARAGE_ENTRANCES`: x 15, y 162 and y 114; the same on all floors) line up with the stairwell door of the garage turned half a turn, so the strip is two walled 48 m blocks (y 132 to 180 and 84 to 132). `stripPart(layout)` is column 0 of the generated garage without its stairwell door, booth and "Escalera" sign, the opening cut out of its west wall (which stands just inside the mall's wall), and its doorways to column 1 walled up (`gapWalls`; decided by Augusto: the strip is closed, nothing outside shows). The maze always gives the entry cell a solid east wall and open north and south walls, so the player comes in facing a wall and turns left or right; the runtime draws it (`buildStrip`, a clone per opening and floor: 6, sharing geometry and materials, 0.015 m above the floor), makes its boxes solid while the player is in a block (`stripBoxes` + `resolveGarage`, after the mall's own collision), and closes the strip on the shadow's map (`NavGrid.blockRect`). The floor-2 secret door at the south end (y 84) is the strip's other hole: that block's copy has a 3 m gap in its far wall (`stripPart(layout, true)`). What differs between the strip and the garage's column 0 is listed as seam points every 0.5 m (`stripSeams`: the opening and the secret door's gap, and each doorway to column 1); `seamSeen` says whether any is on screen: inside the view cone (the screen's horizontal half angle at the running FOV, plus 6°; looking more than 50° up or down counts as seen) and not hidden behind a wall or column both worlds share, or within 0.6 m. Once the player is 2.5 m inside a block (`stripBlockAt`) and the opening (and secret door) is unseen, the runtime swaps (`swapToGarage`), with no blink: the player's position and facing are turned half a turn into garage coordinates (`stripToGarage`: garage x = 15 - x, y = opening y + 18 - y), the mall and strip hide, and the garage shows with its column-1 doorways walled like the strip's (`GarageView.setGapWall`, collision in `garage.solid`); each then opens as soon as it is unseen. Turned left or right in the entry cell, the swap comes within about 1.5 m (checked by the test). On floor 2's south block, toward the secret door, the door is in line down the column, so the swap waits until the player is out of that line. Answering the payphone (`garageReleased`: sanity back to 0.75 at least, the drain and the ringing stop, `garageDone`) reverses it: with the player in the part of column 0 that the closed strip joins to the opening (`stripRows`), the doorways wall up again one by one while unseen, and once all are walled and the opening is unseen the same swap works backwards (`swapToMall`); they then stand in the strip with the opening restored, and no swap into the garage happens again until they have left it (`stripHeld`). The way in is remembered (`stripEntry`) so the player returns by the opening and floor they used. Debug: `?stripswap=off` (stay in the dressing, for screenshots), `?forcerun=1` (the game runs without pointer lock, for scripted walks), `?released=1` with `?area=garage`, `npm run shots` has `strip_*` views; the stats overlay shows the area and position. It can also be entered by debug key **P** / `?area=garage` (`?x ?y ?yaw` then place the player in garage coordinates). In the garage sanity drains 1/220 per second on top of darkness (standing under a working tube counts as light), the payphone rings every 3.4 s from 8 s in (`audio.ring`, positional, the way to go), reaching it (2.4 m) answers it (see above: the way back is the strip's first column), and sanity at 0.02 is a faint (wakes elsewhere in the mall, as the fail card does). Manual saves are refused in the garage. Not built: the wrong-floor elevator (no elevator exists yet; the door is the way in), hiding in the abandoned cars (own card), the win condition at the payphone (own card: payphone, then the ramp out), signs and arrows fading with sanity.
- `src/engine/auto-quality.ts` — the graphics preset picks itself (no DOM, tested by `npm run test:quality`). Order: `?quality=` (debug) > the player's own choice from the pause menu (`elmallvivo.quality`) > where the game settled last time (`elmallvivo.quality.auto`) > a first guess from the device (`pickInitialQuality`: a software renderer such as SwiftShader or llvmpipe: low; 2 cores or 2 GB: low; 4 cores or 4 GB: medium; a phone: low, medium if it has 8 cores and 6 GB, never high; else high). While no choice is fixed, `FrameGovernor` watches the real frame times of the player actually playing (not paused; frames over 0.5 s are hitches and ignored): after 6 s of grace it judges every 3 s window, and under 28 fps it lowers the preset one level (then 6 s of grace again), saves where it landed, and tells the HUD ("El juego iba lento: calidad gráfica bajada a ..."). It never raises the preset. A pause-menu choice turns it off. `?autoquality=off` disables the governor. `npm run shots` pins `&quality=high` because headless Chrome has a software renderer.
- `src/engine/load-progress.ts` — the loading screen's number (no DOM, tested by `npm run test:load`). `LoadProgress` takes weighted tasks (mall 5, props 4, baked occlusion 0.3, nav 0.3, the loose chair and bin 0.6, shader warm-up 2), each reporting `loaded / total` (the mall by bytes, props by pieces) and finishing when done (also when it failed or is optional, so a missing nav.json never holds the screen); the value never goes back, and reaches 1 only when every task has finished. The runtime reports it through `onLoad({ progress, ready, error })`; `GameCanvas` shows a full-screen bar and percent until `ready`, hides "Clic para jugar" until then, and shows a message with a reload button if the mall itself cannot load. `?loading=<0 to 1>` holds the screen at that progress (design, screenshots; `loading_screen` in `npm run shots`). Download size at the time of writing: the mall 1.2 MB, the kit pieces 1.0 MB (all six files; the game fetches the five placed ones and the chair and bin), the rest under 50 KB, plus the JavaScript (1.4 MB raw, about 385 KB gzipped).
- Shader warm-up (in `runtime.ts`, `warmUp`): after the mall, props and nav have loaded, everything that can ever appear (the shadow, the guard, a loose chair and bin) is made visible once, `renderer.compileAsync(scene, camera)` builds every program, they are hidden again, and the post-processing passes render one frame, so no material compiles for the first time in the middle of play. `?precompile=off` skips it for comparison; `?stats=1` shows `peor cuadro` (the longest frame in the last 5 s window) and `precarga` (ms the warm-up took). Not confirmed on a real GPU: the numbers so far come from a software renderer, where a first-use compile cannot be told apart from everything else being slow.
- `src/engine/night-noise.ts`, `src/engine/noise-view.ts` — night noises (tested by `npm run test:noise`). Things knock over when the player is not looking: a timer (`NoiseDirector`: first event 18 to 35 s in, then every 35 to 80 s, divided by 1 + 0.6 × the sanity shift level, so the mall is noisier as sanity falls) picks a kind (chair tips over 45%, chair scrapes 30%, bin falls 25%) and a spot (`pickNoiseSpot`: beside a random table on the player's floor, 6 to 24 m away, walkable, and unseen: behind a wall or outside the camera view). The motions are hand-written, not a physics engine: `Tip` is a pendulum falling about the base edge with up to two bounces, `Slide` is a push slowed by friction (stops at walls and voids). `noise-view.ts` clones the near meshes of a kit piece into a pivot group (`chair_loose`, a new piece with no placement, and `trash_bin`), keeps up to 8 loose objects (the oldest unseen goes first), and they stay where they land. No collision with the player. Sounds: `audio.clatter` (a crack and a ring, louder with the impact) and `audio.scrape`, positional. Debug: **N** makes one now, `?noise=off` stops them, `?noise=now` brings the first in 3 s, `?noiserest=1` starts with three already fallen ahead (screenshots, `noise_aftermath`). Not built: trays and other props, the shadow reacting to the noise, more kinds.
- `src/engine/guard-scene.ts`, `src/engine/guard-view.ts` — the guard's opening scene (CLAUDE.md, "Opening and the guard"; tested by `npm run test:guard`). It is scripted, not gated on where the player looks: from the first frame after the first pointer lock the player cannot move or look around (`controlLocked`), the flashlight starts off, and the camera turns smoothly to the guard (`LOCK_TURN` in `runtime.ts`). `GuardScene` is the timeline: `holding` (1.2 s standing 7 m ahead) → `approaching` (he walks up at 1.3 m/s and stops 2.4 m away; blocked, he talks where he is) → `talking` (the lines of `es.guardOpening`, 0.055 s per character with a 0.7 s gap) → `farewell` (1.2 s pause) → `lingering` (control returns here; he stays where he is and is gone only 0.4 s after he leaves the view, however long that takes). `placeAhead` picks where he starts: 4 to 8 m straight ahead of the player on open floor in sight (at the real start: 7 m north, in the lobby). The runtime runs it on the first pointer lock when the game starts with no debug position (`?x ?y ?floor`), `?guard=off` skips it, `?guard=now` plays it from wherever the game starts; a load or a floor jump ends it; `progress.guard` becomes 1 once it has played (0 = not met; the guard win card builds on it). Subtitles go to the HUD through `onSubtitle`; controls tips go through `onTip`: "WASD para moverse · Ratón para mirar · Shift para correr" from the moment control returns until he is gone, then "F para linterna" until the player turns the flashlight on (or 14 s); the words are in `es.guardOpening` (genre neutral: usted and "le"; for Augusto to review). `guard-view.ts` draws him from `public/models/guard.glb`, a realistic rigged character made with MPFB (MakeHuman for Blender) and animated with clips retargeted from Quaternius' Universal Animation Library, both CC0 (built by `scripts/guard/build.sh`, see `scripts/guard/README.md`; committed, not part of `npm run assets`). He follows the photo `reference/photos/entrance_concourse-near-entrance.jpg`: stocky, short dark hair, grey short-sleeve shirt, black knit vest, black trousers and shoes, plus a navy "SEGURIDAD" cap and a brass shield badge on the vest (both modeled by script in `scripts/guard/gear.py`). The runtime passes a pose (`walk` while he comes up, `talk` while a line is up, `idle` otherwise); his left arm always plays the torch clip and holds a flashlight built in code, aimed ahead of him, with his warm point light at its lens (the light lives on an always-visible root at intensity 0 while he is away, so no shader recompiles). Until the model has loaded, or if it fails, a stand-in built from primitives is drawn. No voice or sound yet (keys and radio belong to the guard rounds card).
- `src/engine/fail.ts` — failing and coming back (no DOM, no Three.js, tested by `npm run test:fail`). `Fail` is a small timeline: `falling` (0.9 s caught, 2 s fainting; controls locked, screen fades to black) → `dark` (1.4 s; the runtime moves the player at its start) → `waking` (2.6 s; control is back as the picture returns). Being caught by the shadow restores the `checkpoint` save (full sanity and flashlight, like a load) or, if the player never entered an atrium, the start of floor 1. Fainting (sanity at 0, anywhere in the mall; debug key **G** triggers it too) wakes the player somewhere else in the mall (`pickWakeSpot`: random open floor 25 to 120 m away on any floor, from nav.json), sanity at 0.55, nothing lost. The black is a plain DOM overlay in the runtime (works on the low preset, which skips post-processing). The shadow is frozen while the player is locked, and reset (absent for 40 s) on every respawn.
- `src/engine/hiding.ts` — hiding spots (no DOM, no Three.js, tested by `npm run test:hiding`). A spot is a piece the player crawls into with **E** ("Presiona E para esconderte"; E again to come out). The first kind is the food court table: the spots are picked from the placed props (`HIDEABLE`: 30% of `table_set`, seeded, so the same tables every run; no second list to keep in step), the player enters from either end of the table when within 1.1 m of it and facing it, ends up 0.28 m from the centre under the top, with the eye at 0.55 m and the view turned to look out of the end (it may turn 65° either way, up to 57° up). The crawl is 0.8 s in and 0.6 s out and replaces walking (no collision, no movement input). `Hiding.hidden` (true from halfway in to halfway out) is what the runtime hands the shadow as `PlayerSense.hidden`; going in also turns the flashlight off and F does nothing while hidden. `PlayerStatus.prompt` (`interact` / `hide` / `leave`) replaced `canInteract`. More kinds (abandoned cars in the garage, counters) add a rule to `HIDEABLE` and their own entry geometry. Debug: `?hide=1` starts already hidden in the first spot on the starting floor; `npm run shots` has `hidden_*` views. Not built yet: a rustle sound, a model other than the table.
- `src/engine/nav.ts`, `src/engine/shadow.ts`, `src/engine/shadow-view.ts` — the shadow (CLAUDE.md, "Threats" and "Failure"). `scripts/build-nav.mts` (`npm run nav`, part of `npm run assets`, after `props`) writes `public/models/nav.json` (generated, gitignored, 31 KB): per floor two bit planes at 1 m cells, `walk` (all four 0.5 m grid cells clear floor, not a stair zone, no kit piece within reach) and `opaque` (a wall block or outside; voids, glass and props do not block sight). `nav.ts` (`NavGrid`, no DOM, no Three.js): A* with corner cutting and string pulling, line of sight, random spots; stairs are not on the map. `shadow.ts` (`Shadow`, the brain, tested by `npm run test:shadow`): `absent` → `stalking` → `investigating` → `hunting` → `searching` → vanishes. It wanders 12 to 32 m from the player; it notices the player by sight (5 m in the dark, 35 m with the flashlight on, within a 200° view, never through walls) and by noise (7 m walking, 14 m running, through walls), as a building `awareness` (so there is a moment to react); hidden players are noticed only from 1.5 m (`hidden` is set by `hiding.ts`). It hunts at 5.2 m/s (the player runs at 7, walks at 3.2), loses the trail after 6 s without a sight or sound, searches 14 s, then dissolves; the director brings it back 60 to 140 s later, first after 45 s. A floor change makes the mall take it away and bring it back on the new floor. Catching emits `caught` (the runtime shows a provisional notice; the fail-states card makes it a restart). `hunting` is what refuses manual saves. Every number is a named constant in `SHADOW` for tuning. `shadow-view.ts` is placeholder art: a procedural tall faceless figure (a few primitives, one shader material that ignores lights: a black hole under the flashlight, a faint cold rim in the dark, dithered dissolve). The runtime also adds sanity drain while it is in view (0.012/s, 0.03/s hunting), a 5% sanity hit and a low sting when it notices the player, and its positional voice (`audio.shadow()`). Debug: **H** calls it in now, `?shadow=off` (never comes), `?shadow=now` (comes in 3 s), `?shadowat=x,y` (places it on the starting floor), `?stats=1` shows its state; `npm run shots` has `shadow_*` views.
- `src/strings/es-CR.ts` — all UI and in-world text, Costa Rican Spanish.
- `scripts/build-blockout.mts` — the blockout generator; a short orchestrator over `scripts/blockout/`, split by what a part is: `config` (constants, cell classes, plan types), `grid` (plans, rasterizing, cell lookups), `geo` (geometry accumulator and primitives: slabs, prisms, lathes, sweeps, tubes, rocks, boxes), `walls` (edge runs merged into wall quads), `shell` (floors, ceilings, walls, roof), `towers` (stair towers, gardens, elevator piers), `doors` (secret-hallway doors), `palette` (materials), `check` (spawn check, `BLOCKOUT_DEBUG` reachability image), `write` (chunking, meshopt, GLB). The order the orchestrator calls them in is the order of the triangles in the file. Scripts run directly with Node's type stripping: relative imports end in `.mts`, types are imported with `import { type X }`, and no enums or constructor parameter properties.
- `scripts/build-props.mts` and `scripts/kit/` — the kit pieces and where they stand (see "Kit pieces and placement" below).
- `docs/floorplans/` — floor plans and the data the blockout is built from: the plans, `secret_doors.json`, `towers.json` (the open stair towers), `props.json` (where kit pieces stand).

## Commands

- `npm run dev` — dev server
- `npm run lint`, `npx tsc --noEmit` — checks
- `npm run build` — static export to `out/` (relative asset URLs, so it can sit in a subfolder)
- `npm run blockout` — regenerates `public/models/mall_blockout.glb` from the floor plans
- `npm run props` — regenerates the kit piece files (`public/models/kit/`) and `public/models/props.json` from `docs/floorplans/props.json`
- `npm run assets` — both of the above; run it after changing plans, towers, doors or props. Its outputs are gitignored: `npm run dev` runs it first if any is missing, `npm run build` always runs it
- `npm run test:walk` — rebuilds the assets (`npm run assets`), then walks a simulated player through it with the game's own collision: the three stair sets climb from floor 1 to 3, the sealed set's gate holds, no atrium edge or solid block can be walked through (about 8,000 attempts, a few seconds), and every placed prop stops the player from all four sides. Run it after any change to the builder or `walk.ts`. With the old chunk-name bug it reports hundreds of failures.
- `npm run pieces` — after `npm run props`, renders every kit piece with the game's materials (solid, wireframe, from behind, a flashlight close-up, and the far version solid and as a wireframe) into `shots/` (`ONLY=bench_red,trash_bin` for some)
- `npm run shots` — after `npm run build`, screenshots the fixed views into `shots/` (gitignored) with headless Chrome and software rendering; edit the `VIEWS` list in `scripts/shots.mts` to add views. For checking looks by eye, not a pixel comparison.

## Optimization plan (running name)

Order: (1) chunk and compress the blockout, (2) split the builder into modules and add automated walk/screenshot checks, (3) kit pieces and placement JSON, (4) exterior panorama and baked vertex AO, (5) area streaming. Layers: shell, collision, kit pieces, area decoration, hero areas, garage. Split by what a part is, not by floor.

**Step 1 (done): chunks and compression.** `scripts/blockout/write.mts` cuts each material's geometry into chunks (storey x 48 m square, `CHUNK_SIZE` env to try other sizes; triangle goes to the chunk holding its centroid), so three.js frustum culling can skip them. About 270 chunks. Every chunk node keeps the material name, because the material name identifies what a chunk is. The GLB is written with `EXT_meshopt_compression` (3.5 MB to about 1 MB). Positions stay plain float32 on purpose: the collision BVH is built from them. Normals are quantized, and the runtime drops them for collision anyway. `GLTFLoader` needs `MeshoptDecoder` (set in `runtime.ts`).

**Step 2 (done): builder modules and automated checks.** The 1,200-line builder is split into the modules listed under Layout, with byte-identical output (checked by hashing the GLB before and after). Collision and ground-following moved out of `runtime.ts` into `walk.ts` so the game and the test share one implementation. `npm run test:walk` and `npm run shots` are the two checks. The tower list later moved to JSON (step 3). Git LFS was dropped (see CLAUDE.md, Repository conventions); instead every generated asset is gitignored and built before `next dev` (if missing) and `next build`. The build is deterministic, so a fresh checkout gets byte-identical files.

## Kit pieces and placement

For things that repeat (now: food court table sets, red padded benches, waste bins, planters with plants, the tray-return stand; shop fronts, elevator cars and garage chunks later). Three parts, each with one place to edit:

- **The piece** (`scripts/kit/pieces.mts`): a function that builds one piece around its own origin (x and z centred, y = 0 on the floor) as geometry per material, plus a collision box and a clearance radius. `npm run props` writes each to `public/models/kit/<name>.glb`: one node per material, and a node called `collider` with the invisible `barrier` material. **A hand-modelled file with the same layout can replace a generated one without touching anything else.** The collider box has to reach chest height (the player's collision sphere sits at 1.0 m), so a table's box is 1.3 m tall even though the top is at 0.75.
- **Where they stand** (`docs/floorplans/props.json`, hand-edited): `scatter` rules fill an area (a plan polygon such as `south_area`, or a box) on a grid with jitter, a turn limit, a skip chance, a required aisle and a seed; `place` puts one piece at one spot. `scripts/build-props.mts` checks every instance against the floor grid (clear floor all around, with the aisle, no stair zone, 3 m from any secret door) and drops the ones that fail, printing how many and why. The random numbers are drawn for every grid spot whether or not it is placed, so changing one rule never reshuffles the others.
- **Wall pieces:** a piece marked `wall: true` stands with its back (local -x) against a wall and its front facing out; its collider's `hx` is its half depth. A scatter rule with `"wall": true` finds open floor along walls (never stairs, elevators or escalators), shuffles the candidates with the seed, and places up to `max` per floor at least `spacing[0]` m apart. Every placement also drops if it would overlap another piece (radius against radius).
- **In the game** (`public/models/props.json`, generated): per piece, flat `[x, y, z, yaw]` groups. `props.ts` loads each piece once, draws it with a near and a far `InstancedMesh` per floor and material (see step 5), and builds each instance's collider as plain positions in world space (not a clone, so how a file stores its vertices cannot break the merge into the collision BVH). A missing or broken props file does not stop the mall from loading.

**Detail standard:** pieces must reach the level of the reference repo's props in shape, ornament, hardware and texture; see "Kit piece detail standard" in `docs/art_style_reference.md`. They are built from the soft primitives in `scripts/kit/soft.mts` (`softBox`, `loft`, `turned`, `tubePath`, `plate`, `placed`, `warped`; and for ornament and hardware `band` and `cord` for moldings round a box, `sweep` along a `rectPath` for framed panels, `boltHead` with `oriented`), never from plain boxes. **Wear bake:** `scripts/build-props.mts` splits every edge longer than `REFINE` (0.3 m), then `scripts/kit/wear.mts` ray-casts occlusion per vertex against the whole piece, the floor and (for wall pieces) the wall, and measures convex and concave curvature. It writes them as a `_WEAR` vertex attribute (`_wear` in three.js). Leaves also carry `TEXCOORD_0` (along, across). `materials.ts` reads both when present: wear layers per kind (chips, rubbed edges, crazing, cup rings, streaks, rust low down, grime, floor dirt, dents) and a baked occlusion that dims the ambient light. The shader cache key includes `-wear` and `-leaf`. Kit files are welded and meshopt-compressed; `npm run props` prints sizes and triangle counts. `npm run pieces` serves `materials.ts` to its viewer with Node's type stripping, so the shots show the real styling. The table set (four chairs) is about 17,000 triangles × 39; each piece also gets a far version (step 5).

`scripts/blockout/paint.mts` (`paintGrid`) is the one list of steps that change the floor grid after the plans are rasterized (stair zones, the bridge arc). The builder, the props builder and the walk test all call it. A new painting step goes there, never in a caller, or the three will disagree about the mall.

**Step 3 (done, first pass): kit pieces and placement.** Done for one piece, the food court table set (38 on floors 2 and 3). Also done: the tower list moved to `docs/floorplans/towers.json`. Generated kit files and `props.json` are build artifacts, not committed (step 2). Next kit candidates: restaurant shop fronts, the elevator car, wall TVs, the cinema food stand counter.

**Step 4 (done, first pass): exterior and baked occlusion.**
- **Exterior** (`sky.ts`): see Layout. It replaces the flat dark backdrop behind the glass. The look is a first pass for Augusto to judge; the street layout, building ring and lights are all numbers at the top of the shader, and nothing in it is the real surroundings of the building.
- **Baked occlusion** (`scripts/blockout/ao.mts`, `public/models/ao.png`): a deliberate change from "baked vertex AO". The shell's floors and ceilings are a few huge quads, so vertex AO would have meant subdividing the whole mall (many times the triangles). Instead the builder writes a small grayscale map in plan space (one pixel per 0.5 m cell, the three floors stacked, 7 KB), and `materials.ts` samples it by world position for floors and ceilings (ceilings at 0.6 strength). It dims only the ambient light, never the flashlight. Solid cells and enclosed gaps occlude with a 2.5 m falloff; holes and the outside do not. The low preset has no surface detail, so it has no occlusion either. The image is loaded with `flipY` off: image row `floor * 420 + plan row`. Walls keep their height-based fake occlusion in the shader. Not covered: kit pieces and stair treads.
- `ONLY=name1,name2 npm run shots` renders only those views.

**Step 5 (done, first pass): drawing only what is seen.** Measured first: the whole download is under 2 MB (mall 1.2 MB, kit pieces about 1 MB), but the kit pieces were about 1.16 million triangles against 71,000 for the mall shell, and every piece on a floor was drawn whenever any of that floor's group was in view. So this step is about drawing, not downloading:
- **Far versions** (`scripts/kit/lod.mts`): `npm run props` adds a simplified copy of every part to each piece file as `<material>_far` nodes. It welds the generator's per-quad vertices, then meshoptimizer simplifies to 1 cm (`FAR_ERROR`), pruning parts smaller than that (bolts, rivets, glides). Normals, the baked wear and the leaf coordinates are weighted attributes; the wear weight is high (0.1) because a lower one smoothed the dirt off the bench back and made a visible pop. Table set 17,360 → about 2,800 triangles, bench 12,074 → about 600. A hand-made file without `_far` nodes is drawn near at every distance.
- **Per instance, every frame** (`props.ts`, `update()`): each instance goes to the near or the far `InstancedMesh` (one shared matrix buffer per version, uploaded only when the set changes), or is skipped when its bounding sphere is outside the view or past the fog (`fogFar`). The LOD distance is per quality preset (`lodDistance`: 6, 8, 12 m), with 1 m of hysteresis so a piece at the edge does not flicker. Colliders are unaffected: every instance collides, drawn or not.
- **Measured** (`npm run shots`, views `lod_foodcourt_near` and `lod_foodcourt`, food court on floor 2): 566,000 triangles with every piece near against 176,000 with the switch, with no visible difference in the shot.
- **Not done, on purpose:** the mall chunks are not hidden by distance, because a far wing seen through glass is a fog-coloured silhouette against the sky, and hiding it would show sky through the building. Splitting the download into per-area files waits until there is enough to split: hero areas and the garage (its own level, loaded with its fade transition).
